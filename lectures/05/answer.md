- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  `uv run python -m app.retrieval "LoRA QLoRA 違い"`を実行したところ、第2回・PDF p.52が第1位、p.51が第2位に取得された。p.52では、LoRAは元の重みを固定して小さな行列A・Bだけを学習し、QLoRAは元の重みを4bitに量子化することを確認できた。p.51では、Full Fine-Tuning、LoRA及びQLoRAの違いを比較できた。一方、p.60、p.47、p.61は関連用語を含むものの、今回の質問への回答には必須ではなかった。

- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  ベクトル検索では、`search_materials({"query": "LoRA 固定 学習 QLoRA 追加"})`が1回呼び出された。Treeでは、`browse_tree`が4回呼び出され、講義一覧、`lec02-main`、`lec02-main-s045`、`lec02-main-p052`の順に目次をたどった。Graphでは、`search_graph({"query": "LoRA QLoRA 固定 学習"})`が1回呼び出された。全文投入ではツールは呼び出されず、資料全体が直接モデルへ渡された。

- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  今回の質問では、4方式とも回答に必要な情報を取得でき、根拠不足による明確な失敗はなかった。ベクトル検索では最大5件のうち、p.60、p.47、p.61は回答に直接必要ではなかったが、最終回答では主にp.51、p.52を適切に使用できた。全文投入では必要なページを取得できていたものの、質問へ直接答えず、資料を確認するためのヒントとして回答した。

- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  今回のように用語が明確で、答えが特定のページにまとまっている質問では、ベクトル検索を採用したい。全文投入と比べて入力トークン数を大幅に削減し、最も低い推定費用で正確に回答できたためである。Graphは最短時間で回答できたが、ベクトル検索より入力トークン数と費用が多かった。Treeは探索経路を確認しやすい一方、ツール呼び出しとモデル応答の回数が多く、時間と費用が増えた。ただし、全文投入とほかの方式では対象資料の範囲が異なり、実行は各方式1回のみであるため、この結果だけで方式全体の優劣は判断できない。

- 気づき・疑問：
  RAGでは、資料全体をモデルへ渡さなくても、質問に適したページを取得できれば、少ないトークンと費用で正確な回答を生成できることが分かった。一方、検索結果には、用語が似ているだけで質問への直接的な根拠にならないページも含まれていた。取得件数を増やせば根拠が充実するとは限らず、必要なページを適切に選択して回答へ利用できるかが重要である。また、Treeは探索過程を説明しやすく、Graphは関連情報を広げられるため、質問の種類に応じて取得方法を使い分ける必要がある。

- 取り組んだレベル：基礎

- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  `app/config.py`の`RAG_TOP_K`を5から2へ変更し、通常のベクトル検索で返すページ数を減らした。索引は再作成せず、変更前後で同じ質問を`--trace`付きで実行した。

- 比較した質問と、固定した条件（モデル・対象資料など）：
  「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」を使用した。モデルは`gemini-3.5-flash-lite`、対象資料は第1～3回の本講義資料214ページ、検索方式は通常のベクトル検索で固定し、`RAG_TOP_K`だけを変更した。

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  変更前後とも、`search_materials`が1回呼び出され、LoRAは元の重みを固定して低ランク行列A・Bだけを学習し、QLoRAは元の重みを4bitに量子化すると正しく回答した。引用根拠も、いずれも第2回・PDF p.51、p.52であった。変更前は19.26秒、入力3,031 tokens、出力194 tokens、モデル応答2回、推定費用0.001394 USDであった。変更後は2.22秒、入力1,741 tokens、出力172 tokens、モデル応答2回、推定費用0.000952 USDとなった。

- 改善した例と、残る失敗・制約：
  今回の質問では、検索件数を2件に減らしても必要なp.51、p.52が上位に残り、回答と根拠を維持したまま、入力トークン数を約42.6%、推定費用を約31.7%削減できた。一方、複数ページや章をまたぐ質問では、2件では必要な根拠が不足する可能性がある。また、実行時間は約17秒短縮したが、APIの混雑状況等にも左右されるため、1回の測定だけでは検索件数変更の効果と断定できない。

- 気づき・疑問：
  検索件数は多ければよいわけではなく、質問に必要なページを上位で取得できる場合は、件数を絞ることで回答品質を保ちながらトークン数と費用を削減できると分かった。一方、適切な件数は質問ごとに異なるため、単一の固定値ではなく、質問の複雑さや取得結果に応じて件数を調整する方法も検討する必要がある。
